# 피드백 채점 프롬프트

공통 기준은 `backend/services/feedback_prompts.py`의 `GRADING_RULES`에서 수정합니다.
`MATERIAL_SYSTEM_PROMPT`, `SCRIPT_SYSTEM_PROMPT`, `OVERALL_SYSTEM_PROMPT`가 이 기준을
공유하며, `ai_feedback_method.py`의 세 생성 함수가 각 프롬프트를 사용합니다.

## 기본 기준

| 평가 항목 | 배점 | 확인할 내용 |
| --- | --- | --- |
| 목적 적합성 | 25 | 명시된 목적과 청중에 맞는 메시지·내용 |
| 내용과 근거 | 25 | 설명·맥락의 충실성, 주장에 적절한 근거·사례 |
| 논리 구조 | 25 | 도입·본론·결론, 연결, 핵심 누락·모순·반복 |
| 전달 명료성 | 25 | 자료의 가독성·배치 또는 대본의 문장·용어 설명 |

네 항목을 각각 평가해 합산하도록 지시합니다. 90점 이상은 네 영역 모두 우수하고
목적 달성을 방해하는 중요한 문제가 없을 때 부여합니다. 목표 평균이나 고정 점수에
맞추지 않으며, 제출물에서 확인할 수 없는 결함을 만들어 감점하지 않습니다.

기존 프롬프트의 85점 예시와 장점 2~3개 강제 지시를 제거했습니다.
장점이 없으면 빈 배열을 허용하고, 같은 문제의 중복 감점과 수정 대본을 기준으로
원본 점수를 높이는 일을 금지합니다. 자료에 포함된 점수 지정 지시도 따르지 않습니다.

평가 항목별 지침과 점수 구간은 프롬프트에만 존재합니다. 응답 스키마는 바꾸지 않으며
`score`, `feedback`, `strengths`, `improvements`, 대본·슬라이드 필드를 그대로 사용합니다.
프롬프트는 `sum(improvements[].deduction) == 100 - score`를 요구하지만, 현재 응답
모델이 이 합계를 프로그램으로 강제하는 것은 아닙니다.

## 변경 시 확인할 점

1. 부족한 자료·보통 자료·좋은 자료를 고정하고, 발표 목적도 함께 고정합니다.
2. 같은 모델과 설정으로 변경 전후를 반복 비교합니다.
3. 점수 순서, 감점 합계, 실제 근거, 없는 문제나 칭찬의 생성 여부를 함께 확인합니다.
4. 자료만·대본만·종합 입력을 따로 확인하고, 관찰할 수 없는 음성·디자인을 평가하지 않는지 봅니다.

소규모 비교에서는 현재 설정 모델 `gemini-3.1-flash-lite`로 합성 대본 두 개를 각
변경 전후 1회 평가했습니다. 일반적인 AI 장점만 나열한 대본은 70→45점,
관찰 기록·한계·검수 방법·시범 운영 조건을 포함한 제안 대본은 85→92점이었습니다.
변경 후 두 응답 모두 점수와 감점 합계가 일치했습니다. 이는 소규모 관찰 결과이며
실제 사용자 자료의 정확도나 반복 실행 시 같은 점수를 보장하지 않습니다.
특히 실제 발표자료와 종합 입력은 대표 사례로 추가 비교해야 합니다.

새 기준은 새 실제 분석에 적용됩니다. 과거 DB에 저장된 점수와 고정 JSON을 반환하는
`/mock/upload/`의 샘플 결과는 바뀌지 않습니다. Vercel 프런트 배포만으로는 서버의
시스템 프롬프트가 바뀌지 않으며 Azure 백엔드에도 새 코드를 배포해야 합니다.

프롬프트 변경은 관찰 결과를 보고 조정합니다.
[Google 프롬프트 설계 안내](https://ai.google.dev/gemini-api/docs/prompting-strategies)를 참고합니다.
